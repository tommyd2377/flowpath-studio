# General visitor task execution

## Required outcome

Chat and voice represent the same publisher website and complete a visitor task through enabled capabilities. The model resolves dependencies from actual results, not subject-specific routing or hard-coded action pairs. Finding an address and displaying a map is one acceptance case; retrieval, comparison, image search and display must compose through the same mechanism.

## Current verified implementation and gaps

- `lib/visitor-knowledge-context.ts` supplies the website-assistant role, publisher boundaries, full-task instructions, evidence rules and screen acknowledgment requirements to both channels.
- `lib/visitor-task-runner.ts` is the website-owned, transport-independent executor. It accepts chat or voice delivery, runs sequential tools and returns their outputs to the next model request. The mirrored `lib/gpt-live/backend.ts` remains unchanged for the independent news app. It remains bounded to four tool executions plus a final model response, with no parallel tools or automatic retries.
- `lib/visitor-realtime-control.ts` previously overrode that limit to one. It now calls the website executor with four steps and continues to wait for browser acknowledgment before returning display results to the model. Per-request usage is recorded by the existing callback. This increases the maximum model requests per voice task from two to five; it adds no background work.
- Explicit `silent` and `directText` results still terminate a task; current failure outcomes must not be converted into successful prerequisite results.
- Live workspace chat now streams through `lib/visitor-chat-task.ts` and the shared executor, using the existing publication-bound control mailbox for browser acknowledgments. `lib/visitor-chat-protocol.ts` validates the bounded NDJSON stream. The legacy provider remains for non-workspace and demo paths.
- `components/VisitorAssistant.tsx` preserves direct Home/Browse controls and routes live chat requests intact to the executor. It applies each streamed view, confirms the resulting state, and acknowledges it before the next step. Missing search views cannot report applied.
- Map tools currently provide published coordinates or an approximate model-selected overview. Resolving a sourced external address and an appropriate map requires reusable evidence/location capabilities, not an address/map regex shortcut. No subject-specific map shortcut was retained.

## Next implementation boundary

Chat and voice share the executor, workspace validators, exploration validator/provider and publication checks, while retaining separate transport adapters. Further consolidation of adapters remains possible. Dynamic instructions are regenerated before every model round from the latest acknowledged workspace, preventing the initial snapshot from overriding newer tool results. The host must own a task ID, publication snapshot, allowed tools, intermediate evidence, latest browser state, cancellation and a bounded execution budget. Tool results must distinguish retrieved information from browser-applied changes. Chat must acknowledge a displayed change before the executor claims success or uses that changed view as a prerequisite. Publication changes, Home, manual interaction and cancellation invalidate stale work. External evidence remains temporary and attributed, not published knowledge.

## Foreground coordination

Floating workspace cards and persistent query results render in different host surfaces. Previously a task result could acknowledge successfully underneath a floating card, and the task capability's Home only hid query results. Back also returned the workspace stack even when the displayed detail belonged to the task surface.

- `SiteExperience` shares the current workspace handle with `VisitorAssistant` and supplies `VisitorTasksProvider.beforeShow`. Valid current task displays return all floating layers before mounting results, preserving the open objects. The server's explicit `VisitorTaskView.navigation: 'home'` also restores the publisher opening; it does not depend on labels or a particular publisher. Stale views are rejected before changing the foreground and rechecked after asynchronous transitions.
- `VisitorWorkspace.releaseFocus` waits for exit animations. Voice Back dismisses an open photo/search overlay first, then returns the floating stack; when no floating layer is open, `VisitorTasks.back` returns a task detail to its existing query, or returns Home from the query. Home awaits task completion and cancels pending local task work. Back/Home refresh the task revision because backend reads/accounting can advance it without a display, while rejecting a changed generation. Comparisons opened through navigation take focus instead of staying underneath the previous card.
- `workspaceElementVisible` is shared by task acknowledgments, ongoing task viewport observations, and visitor screen capture. Clipped, inert, hidden, and fully covered records cannot count as visible. Task viewport observation includes portalled foreground changes, and Home acknowledges an empty scene only after results have exited.
- `captureVisitorContext` includes the owning workspace's portalled content and reports the foreground source/entity even when keyboard focus remains on the microphone or chat. Instructions distinguish foreground focus from retained background objects.
- The Voice/Chat switch remains above nonmodal cards while scrolling. The shared workspace also reserves space for these host-marked controls and the chat composer. Opening a different foreground object dismisses an old photo/search overlay without treating the programmatic dismissal as new user input.

The regression fixture uses synthetic published records and mocked chat/audio transports with the real local task store and display acknowledgments. It covers desktop and mobile/reduced motion, switching from a floating information card to query results through both channels, task detail Back after an undisplayed backend read, opening a second card and returning, task/chat Home, and rejection of pre-Home results. The photo scene test also exercises voice Back from a lightbox and opening another card through it. This verifies client navigation and synchronization, not live speech recognition or model tool selection.

Separate isolated browser runs passed all 23 visitor-realtime, 10 adaptive-workspace and 3 visitor-task tests, including 10,000-record filtering. Suites used separate temporary workspaces to respect the 12-site cap. The task test now opens the existing Advanced collection tools disclosure and waits for the actual selected state before editing filters. ## Clearing the visitor workspace

The reported “close all three panels” failure exposed two problems: simple clearing unnecessarily depended on model execution, and a bulk close could be rejected when chat or card layout changed the scene revision while the object set remained unchanged. A pure regression reproduced the reported workspace-change error before the fix; the original live model payload was not captured.

- `lib/visitor-navigation.ts` recognizes complete, unambiguous clear requests, including “close all three panels” and “clear workspace”. Partial, conditional and compound requests remain model-interpreted. `VisitorAssistant` routes these local commands before model execution, cancels older work and clears the accepted view without consuming a model request.
- `VisitorWorkspace.clear` applies a fresh empty reset and removes greeting highlights, browsing, focused media and temporary search surfaces. `VisitorTasks.hide` cancels pending local displays and pauses viewport reporting without waiting for task storage; existing manual interruption still invalidates older task work. Saved query/filter state can be reopened explicitly. Home continues to restore the publisher's opening; Clear leaves the visitor workspace empty. Neither deletes publisher data.
- `lib/visitor-realtime-context.ts` and `lib/visitor-realtime-control.ts` expose the voice navigation target `clear` with the existing browser acknowledgment contract. `lib/visitor-workspace.ts` also directs model bulk closes to a single empty reset. Success is reported only after the accepted display is acknowledged.
- `packages/platform-ui/src/workspace.ts` tolerates scene-only drift for an empty reset/replace or a batch closing every current object. Publication, workspace revision, reference validation and idempotency checks remain enforced. A late clear cannot erase objects opened since its base revision; partial closes and mixed operations still require their original scene. Empty accepted batches also release orphaned greeting and external-view state in `VisitorWorkspace`.

All 27 tests in the isolated `visitor-realtime` browser suite passed, including desktop/mobile exact-phrase clearing with zero mocked chat submissions, already-empty clearing, clearing real task results during a simulated task-service outage, and a model-generated all-close batch accepted after layout moved and acknowledged with zero remaining objects. ## Answering questions from published text

On September 13, “what cakes do you have?” failed on the published cake-shop page. A read-only copy of the public page reproduced `Knowledge context exceeds 32,000 bytes` when passed through the shared retrieval function: long website blocks had been added to every selected entity and overflowed the structured-context limit before the model could answer. The menu was present in the publication. The historical model request was not replayed. A long-prose regression also exposed the same overflow while voice prepared its legacy presentation tool description.

- `packages/platform-ui/src/knowledge.ts` supports optional `includeBlocks:false`, preserving structured facts, conflict/temporal/qualification handling and lexical matching over blocks while reporting omitted block counts. `lib/visitor-workspace.ts` and `lib/catalog-presentation.ts` use that projection for planner and fact contexts. Local full-text search keywords are removed from provider record projections so they cannot reintroduce the entire prose payload.
- `lib/visitor-published-content.ts` searches the complete already-published section/entity text. Initial workspace instructions include matching passages. The same read-only `read_published_content` tool is registered and executed by `lib/visitor-chat-task.ts` and `lib/visitor-realtime-control.ts`. The existing publication/cancellation checks run before reading; no private documents, draft proposals or external search results enter this public-text reader.
- Each response contains at most six passages, 1,600 characters per passage and 16,000 serialized UTF-8 bytes including metadata. Results identify the publication, source reference, block, heading, character offsets, total matching passages and next offset. Empty-query reads of an exact reference can page through every original character; ordinary query searches use generic lexical ranking. Heading context accompanies paragraphs, and long summaries receive less ranking weight than matching body text. Existing `visitor_task` record lookup remains the path for canonical collection records.
- `lib/visitor-knowledge-context.ts` tells both channels to answer ordinary questions from published passages, retrieve more when needed, distinguish excerpts from exhaustive lists and preserve published qualifications. Reading content does not require a display acknowledgment, change the screen, imply live inventory or enable an action. Structured facts remain authoritative. No model-round increase, paid retry, dependency, ingestion mutation or publication change is introduced.
- Context-capacity errors now receive a bounded `capacity` diagnostic category, including failures during voice preparation; raw content/errors are not logged.

Tests in `tests/visitor-published-content.test.ts` and the real voice-control fixture cover long cake, service and course pages; initial answer context; a shared read followed by an answer; the actual chat stream; multibyte byte limits and complete pagination; stale, private and cross-publication reference rejection; and no navigation or external search for a read-only question. The real public catalog now produces a 17,397-byte structured projection, with its menu paragraph available in the accompanying bounded text passages. These tests verify retrieval and execution with mocked models/audio; they do not establish live model answer quality or speech recognition.

Final verification: all 47 focused public-content/voice tests, 21 rendering tests, typecheck, independent packed-package verification and production build passed. The full server run had 442 passing tests and one chat fixture failure: it supplied unnormalized stored content instead of the same validated publication returned by the visitor route. Correcting that fixture to use `visitorAccess` passed the actual chat-stream test in the subsequent focused run. The full server suite was not repeated after that fixture-only correction. Logs are `/private/tmp/published-content-check.log` and `/private/tmp/published-content-focus.log`. No paid calls, live speech test, user-site changes or deployment were made. ### Handoff for preserved website imports

The public-content reader currently consumes published `SiteContent` sections and canonical catalog entity `blocks`. It does not read private `artifact.website.captures`, origin baselines, or owner-only layout storage. Website import can remove duplicate source-page entities without changing this contract, provided approved visitor prose remains available in the canonical published records.

The concurrent preserved-layout implementation publishes a separate immutable `WebsiteLayout` through `SiteContent.websiteLayoutRevisionId`. Its sanitized page HTML is not yet an input to this reader. If a reviewed page contains detail that is absent from the semantic catalog, that detail therefore needs an explicit public-text integration before claiming full coverage of the preserved website. Reuse the bounded reader: resolve the current publication first, load only its public layout revision, verify its knowledge-revision binding, project readable page text, and retain exact revision-scoped references and pagination. Do not feed private captures to the assistant or create duplicate visible catalog items solely for retrieval. Cover a fact present only in an approved public page, exclusion of draft/private/unpublished captures, stale-publication rejection, and unchanged read-only chat/voice behavior with mocked transports.

The reported voice-test event-union issue is already corrected to `event.type === 'plan'`; the subsequent focused tests and typecheck passed. This handoff records an integration boundary for the import owner, not completed preserved-layout retrieval or a live-provider verification.
