# Visitor conversations

Publishers choose the experience in **Content → Visitor conversations**: Voice only, Chat only, or Chat and voice. New sites default to Voice only with Premium voice; Off is not offered in the dashboard. Voice quality offers Standard (lower cost) and Premium (more capable). Settings use the existing draft, undo, review, and publish flow. They remain optional in the content schema to preserve legacy published sites. Inactive legacy content is prepared as an unsaved voice-only draft when the editor loads. Its published snapshot is unchanged until the publisher saves and publishes; opening the dashboard cannot enable paid conversations on an existing published site. Existing active chat/voice preferences are preserved.

## Visitor experience

Visitors can browse directly or, when the configured mode permits it, describe what they want through text or voice. The runtime presents collections, typed criteria, detail, comparisons, selections, relationships, registered links and approved photos from the published knowledge/media revisions. Sites without a catalog still render published introductions, content sections, hours and contact details. There is no displayed visitor/assistant chat transcript. Voice can answer directly from the same published information, optionally change the validated view, or scroll to an existing published item. Draft content, private source artifacts and the owner's editor conversation are not included.

Voice starts only when a visitor taps the waveform. Connected published sites use continuous, full-duplex WebRTC: microphone capture stays active between turns, replies stream to the speaker, and speaking interrupts the current reply. Visitors do not record and submit each turn. The waveform uses separate microphone and speaker analysers and follows listening, thinking and playback events. Tap the waveform again, use the fixed **End voice** control, or press Escape to end the conversation. Keyboard End/reset returns focus to the current input control, including Chat after voice exhaustion; touch End preserves the current scroll position. The saved greeting starts only after the browser reports a connected peer, attached remote audio and prepared playback, and the supervising server applies readiness. Readiness has a 25-second server deadline. Greeting is skipped when **Let the visitor speak first** is selected or local history continues an earlier conversation; it is never rendered as a paragraph on the site. This shared implementation applies to catalog and legacy published sites, without depending on the separate FlowPath news app.

Chat and voice retain the current view and bounded local conversation history across mode changes and new calls. Voice-only remains the publisher setting and preferred opening mode, but **Continue by typing** is available after a voice error even with voice allowance remaining. The final allowed voice reply finishes playing before quota fallback; Chat then uses its separate allowance. A site that exhausts both allowances keeps its current view and ordinary browsing controls. **All of the site** restores the default view while preserving local conversation history and usage. Catalog filtering, selection, comparison, detail, disclosures and photo viewing do not consume AI attempts. Manual browsing cancels stale generation/playback, reports the new validated state and keeps the audio session connected.

The dashboard preview always uses deterministic demo replies and, where available, an installed local device voice. It never requests a microphone or contacts OpenAI. Published sites on the local demo backend are also deterministic. Firebase sites require the existing OpenAI connection (`VOICE_AI_MODE=openai`); unavailable configuration fails closed. No environment, authentication, deployment, or billing settings are changed by this feature.

## Component selection and motion

Publishers may separately enable [Search and explore](search-and-explore.md) for external web results, web images and interactive map overviews. These views are labeled separately from published knowledge and never edit it. Typed and voice search share a separate search allowance; opening an existing image or zooming uses local controls. The voice assistant waits for a browser acknowledgment before describing a search view as displayed. This capability is off by default.

For catalog sites, the model returns a strict ready/unavailable envelope containing a versioned `PresentationPlan`. The plan has a snapshot ID, operation, semantic transition and up to eight controlled components, one of each type. It references existing entities, typed attributes, collections, registered capabilities and approved media. Detail requires one entity; comparison requires two to six entities and at least one declared attribute. Provider instructions ask for useful shared attributes, but schema validity alone does not prove comparison quality. Unknown values remain unknown, and a photo or published schedule does not establish live availability or an executable action.

Both server and browser validate these references and compatible variants. The shared runtime then compiles the plan into local OpenUI grammar, performs bounded preflight/parsing and renders the platform's React components. It does not accept model-generated JSX, HTML, CSS, URLs or business facts, and it does not depend on OpenUI Gateway. Catalog selection remains runtime-owned. An optional strict `stateUpdate: { filters: [...] }` replaces the complete filter set together with the accepted plan; an empty list explicitly resets filters, while omission preserves them. Up to 24 filters use published attributes, compatible operators and typed values. Strict under/over constraints use `lt`/`gt`, and unknown values do not satisfy numeric constraints. Back restores the previous view and filters; an invalid or stale plan changes neither. See [contracts](../packages/platform-ui/src/contracts.ts), [provider envelope validation](../lib/catalog-presentation.ts) and the [architecture](architecture.md).

The legacy path uses a smaller plan with a layout, up to six published source IDs and a ready/unavailable status, plus bounded references for approved galleries. Its comparisons show published descriptions rather than invented metrics. Both paths report unavailable information and preserve the accepted view when a plan cannot be supported.

Responses uses Structured Outputs to select the typed-request view. A Realtime turn can answer directly in one generation or call either `present_site` or `navigate_view` once, followed by at most one continuation with tools disabled. `present_site` selects validated UI; `navigate_view` scrolls to the top, bottom or an already rendered published entity/source and waits up to eight seconds for an applied/unavailable browser acknowledgement. Neither tool can edit, book, send, purchase, access accounts, open external links or execute generated code. Invalid plans fail without a paid repair or retry. A cancelled, failed, stale or malformed response leaves the previous view intact. Manual interaction advances the interaction revision and cancels stale work while retaining the live audio connection.

Suggested requests fill the composer and never send automatically. Enter submits, Shift+Enter adds a line, and composition input is respected. A progress indicator appears immediately; the selected components enter once a complete response has been validated. Failed or cancelled requests return to the composer. Typed and voice requests receive bounded recent history and the current validated legacy presentation or catalog plan/state. During a call, the browser also reports visible published references, expanded sources, focused references, rendered component types and viewport/scroll geometry. These are observations, not proof that the visitor read an item. Passive screen changes update context without cancelling generation on every scroll; explicit manual controls invalidate older work. All of the site restores browsing while preserving local conversation history and usage. Changing draft content resets the preview view and any pending voice/request.

The shared motion vocabulary uses 380 ms reveal, 450 ms disclosure, 480 ms reflow, 520 ms workspace/focus/restore and 180 ms exits. Stable component identities preserve existing controls while surrounding geometry changes; criteria expansion retains the first four controls. Exiting controls become inert immediately. Reduced motion removes movement and looping indicators. Requested destinations scroll into view only if offscreen after their layout settles, and visitor input cancels that pending reveal. See [shared motion](../packages/platform-ui/src/motion.tsx) and [browser regressions](../tests/browser/motion.spec.ts).

The owner preview and demo backend use deterministic matching to exercise the same renderer. Demo matching is not a semantic model and cannot establish live selection quality. Source documents must pass Knowledge review and publication before their semantic records appear publicly. Photos must be applied to the reviewed library and published. Uploading an original alone does not make it visitor content. The [three synthetic fixture catalogs](../fixtures/README.md) exercise the shared controls across different domains.

## Models and limits

| Path | Model | Bound |
| --- | --- | --- |
| Chat | `gpt-5.6-luna` via Responses | One request; 1,200 output tokens for a catalog plan or 700 for the legacy path; 30-second timeout |
| Standard voice | `gpt-realtime-2.1-mini` | One answer/tool response: 1,200 tokens for a catalog or 250 for legacy; after one optional tool, at most one 500-token continuation |
| Premium voice | `gpt-realtime-2.1` | Same bounds, low reasoning effort |
| Input transcription | `gpt-4o-mini-transcribe` | Continuous input ASR supplies bounded cross-mode history; retained recorded-turn callers also use transcription. Separately metered, with no extra answer generation |

Voice replies use `marin`; WebRTC negotiates live audio transport. The Standard/Premium selector changes the model, not the speaker's voice identity. Each continuous session has a server-enforced 120-second wall-clock limit, 20-second idle limit, 20-second maximum visitor utterance, 35-second generation deadline and 30-second playback limit. Greetings remain one response capped at 750 output tokens. A turn using a tool has a combined maximum of 1,700 output tokens for a catalog or 750 for legacy content. A direct answer uses only the first generation. There are no automatic provider retries or reconnects. The existing recorded-turn API remains compatible, using PCM16 at 24 kHz with its previous limits. [Continuous controller](../lib/visitor-realtime-control.ts), [recorded-turn provider](../lib/visitor-provider.ts)

Per-site defaults when enabled are 25 chat attempts and 5 voice replies daily. Publishers can set 1–100 chat attempts and 0–100 voice replies. These are shared across all visitors to the site. The server also caps the entire deployment at 100 chat attempts and 100 voice replies per UTC day. Platform usage can therefore make a site reach its allowance sooner. Counts are separate from the owner's AI editor usage.

A continuous connection reserves its first voice attempt before contacting the provider, even if the visitor stays silent or disconnects. That reservation covers the greeting, or the first response on visitor-speaks-first sites. Each later visitor turn requires another transactional reservation before generation. Failed and cancelled attempts count; there are no refunds or automatic retries that could silently spend again. A UUID replay is rejected. Changing modes or quality, refreshing a page, or clearing a browser conversation does not reset server usage. These are attempt limits, not exact dollar budgets or subscription plans. Continuous input, accumulated provider context and separately metered input transcription also affect cost; preserving attempt/output ceilings does not mean identical cost to recorded turns. Default fallback Chat remains independently capped at 25 attempts per site; it is not an additional allowance.

## Storage and request boundary

`/api/visitor/[slug]` reads the published snapshot and selected model on the server. Clients cannot supply a model, tier, system instructions, or site content. The server checks the origin, message/history lengths, recording bytes and total request body size. Bounded request context can include catalog state/plan, the current legacy presentation, expanded sources and browser screen observations. Catalog state includes the snapshot, filters, selected IDs, focused ID and ordered view IDs. The server validates all entity, attribute, source and media references against the publication before reserving an attempt, rejects conflicting duplicated state, and checks for a publication change at reservation. A process-local 120-request/minute gate limits traffic before storage access. It is not a distributed per-visitor abuse prevention system; anonymous visitors can consume a site's shared allowance.

Firebase usage is reserved transactionally in the server-only `voiceVisitorUsage/current` document, reading `voicePublished/{slug}` in the same transaction. The document keeps the UTC date, counters, and bounded request IDs; it does not store visitor messages or audio. The local demo uses the existing serialized file-store queue and an optional `visitorUsage` field. A corrupt or future-dated ledger fails closed. UTC rollover resets usage automatically, with no scheduler, trigger, or background job. The existing Firestore rules deny browser access; no rule changes are needed.

`/api/visitor/[slug]/session` accepts an audio-only SDP offer, bounded context and up to eight recent user/assistant messages. It rejects video and data-channel negotiation: the browser cannot send provider session instructions or arbitrary tool commands. A server sideband WebSocket owns all response creation with automatic response creation disabled, while provider VAD still interrupts and truncates WebRTC playback. Each authorized turn has at most one optional presentation/navigation tool and one tool-free continuation; a direct answer needs only one generation. The publication is checked before reservation and again before a plan or control update is applied. Interaction and view revisions discard interrupted or obsolete results.

One persistent HTTP response carries the SDP answer, validated plans/navigation requests, availability, bounded transcript events, control acknowledgements and conversation-state events. It includes a short-lived application control capability, but no provider key, provider call ID or audio buffers. Closing that body, exceeding a deadline, or detecting malformed provider output terminates the sideband and calls the provider hangup endpoint. Cleanup is retained with Next's `after` lifecycle. Failed or uncertain cleanup blocks further calls in that process. Additional process-local gates allow four concurrent sessions and 30 starts per minute; the shared transactional attempt ledger remains the cross-process usage gate. These controls are not a completed anonymous-visitor abuse or monetary billing system.

`/api/visitor/[slug]/session/control` accepts capability-scoped, ordered application updates. In Firebase mode a server-private `voiceVisitorRealtime/{id}` document delivers them to the process supervising the active call; worker affinity is not required for these updates. The local implementation uses a single-process in-memory mailbox and is not a distributed backend. Capabilities are bound to the slug, site, publication and expiry; only a token hash is stored. Each call accepts at most 300 updates, reserving its final slot for End, with eight normal updates per second and a 64 KiB update bound. Newer desired state can coalesce older pending state while retaining readiness, End and navigation acknowledgement. A successful control POST means stored, not applied: the owning stream emits `control_applied` after validation/application. The browser has a bounded acknowledgement wait and no automatic retries.

Mailboxes contain bounded current published view/screen state, never history, transcripts or audio. They are deleted on normal close, become unusable at expiry, and expired records receive bounded opportunistic cleanup when another session starts. No TTL policy, scheduler or new background worker is configured. Abrupt process loss can leave an expired private record until cleanup. End sends a best-effort control update as well as closing capture, playback, peer and stream; server deadlines remain authoritative.

Browser capture and playback stop on explicit End/cancellation, mode changes, content changes, unmount, pagehide, or a hidden document. Manual browsing interrupts stale speech and generation without closing the peer. Microphone tracks pause briefly while the new view is being acknowledged, with an updating-view status; only the latest matching acknowledgement reopens capture. This prevents speech and a manual context update from arriving in the wrong order. Late microphone permission results are stopped and discarded. Provider generation completion is separate from audio playback completion; the final allowance is not treated as finished until playback stops or is interrupted.

Continuous voice requires a Node deployment that supports streaming responses, outbound sideband WebSockets and Next's post-response cleanup for the session duration plus setup/cleanup. Deployment adapter timeouts and abrupt process loss require live verification before rollout; local and mocked tests cannot establish that a hosting platform will keep these calls supervised. No deployment settings were changed. The existing FlowPath iPhone startup-echo investigation is separate and was not changed or claimed fixed here.

Cross-mode history is held in component memory (at most eight messages, each bounded to 2,000 characters) and disappears on reload or unmount. It is not rendered as a transcript. User utterances come from input ASR; assistant history is emitted only after the response has settled and playback has finished without interruption. Cleared/interrupted speech is not represented as a fully heard answer. Current view and recent history can seed a new call or typed request, but old audio/provider sessions are not restored. Continuous voice also keeps its active conversation at the provider until disconnect. Catalog browsing has bounded in-memory view history and shortlist; returning to All items preserves selections. Published content/catalog/media descriptions and microphone audio go to OpenAI in connected voice mode. Responses requests use `store: false`; provider retention remains subject to the configured account's policies. The application does not persist visitor audio or conversation history. It records bounded operational events and measured provider usage, with IDs and counts rather than conversation text; see [platform events](../lib/platform-events.ts).

## Verification

Run `npm run check` using Node 24 for lint, types, persistent offline tests, the packed shared-package consumer and a production build. Then run `npm run test:browser` for a fresh headless Playwright context and isolated demo data on port 3225. These commands are defined in [package.json](../package.json) and [Playwright configuration](../playwright.config.ts).

The current tests cover contract/reference bounds, provider envelopes and bounded calls, draft/publication isolation, real OpenUI rendering, manual filtering/selection/comparison, stale and malformed mocked plans, cancelled late results, intermediate motion geometry, mobile/reduced-motion behavior and contextual photos. Provider and Firebase transports are mocked; local persistence and browser rendering are real. See [catalog provider tests](../tests/catalog-presentation.test.ts), [renderer tests](../tests/presentation/runtime.test.ts), [platform browser tests](../tests/browser/platform.spec.ts) and [photo runtime tests](../tests/browser/media-runtime.spec.ts).

Continuous voice regressions cover audio-only signaling, stream cancellation, late call creation cleanup, deadlines, usage reservations, VAD/commit ordering, stale plans, natural interruption and final-allowance playback. The browser tests simulate media and provider events; they do not exercise an acoustic speaker/microphone loop. Live model quality, audio-only SDP interoperability, real microphone/audio behavior, hosting lifetime and Firebase permissions require separate authorized verification. Offline tests do not prove production configuration or provider billing accuracy, and do not authorize paid calls or deployment.

For the current changes, 164 offline server/unit/rendering checks and all 60 browser checks passed, along with lint, TypeScript checking, the production build and packed independent shared-package consumer verification. Browser coverage includes retained calls during manual browsing, context ordering, readiness, chat/voice continuity, page and nested-preview navigation, filter replacement/reset, focus preservation, animation-safe context delivery and typing fallback. The [publisher quality parity audit](publisher-quality-parity.md) records these implemented behaviors alongside unchanged model/session differences and remaining live verification. Continuous transport and offline checks do not establish equivalent acoustic or model quality.

### Published opening and voice dock

Published pages omit the preview banner, voice attribution line, redundant Explore button and template signature. Opening copy defaults to the current catalog title and description, or a local composition from the site name and section titles when no catalog exists. This uses published content and makes no generation request on page load. Content → Opening experience → Opening copy lets publishers select Personalized and edit the headline and introduction; save and publish apply the choice. Existing stored headline and introduction remain available when personalizing.

The shared VisitorVoiceStage uses the Flowpath invitation: a full-height opening, small spaced publisher wordmark with fine side rules, a 650 ms identity fade and a 1.25-second waveform glide into a sticky dock. The same canvas remains mounted. Content sits below the initial viewport and remains available by scrolling without voice. Activation dismisses the opening copy; listening and speaking use waveform feedback plus screen-reader text, while connecting, thinking, map and search work use a measured animated status area. Search progress is emitted only for validated tool work and stale status events are ignored. Reduced motion removes the transitions; the End control and keyboard focus return remain available.

Published pages use the neutral #101110 Flowpath base and restrained charcoal/olive surfaces. Publisher color is retained for identity and controls, not large background washes. The host removes nested page/assistant/catalog width caps, uses 28px desktop and 18px mobile gutters, and fits collection columns to the available width and number of items. It does not constrain desktop content to a phone-sized column. Studio previews keep their own scroll surface.
