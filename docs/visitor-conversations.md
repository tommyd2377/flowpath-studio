# Visitor conversations

Publishers choose the experience in **Content → Visitor conversations**: Voice only, Chat only, or Chat and voice. New sites default to Voice only; Off is not offered in the dashboard. Voice quality offers Standard (lower cost) and Premium (more capable). Settings use the existing draft, undo, review, and publish flow. They remain optional in the content schema to preserve legacy published sites. Inactive legacy content is prepared as an unsaved voice-only draft when the editor loads. Its published snapshot is unchanged until the publisher saves and publishes; opening the dashboard cannot enable paid conversations on an existing published site. Existing active chat/voice preferences are preserved.

## Visitor experience

Visitors can browse directly or, when the configured mode permits it, describe what they want through text or voice. The runtime presents collections, typed criteria, detail, comparisons, selections, relationships, registered links and approved photos from the published knowledge/media revisions. Sites without a catalog still render published introductions, content sections, hours and contact details. There is no visitor/assistant chat transcript. Voice selects from the same information, then speaks about the selected view. Draft content, private source artifacts and the owner's editor conversation are not included.

Voice starts only when a visitor taps the waveform. The saved greeting is spoken first unless **Let the visitor speak first** is selected. The greeting is never rendered as a paragraph on the site or added to the visual result. Later turns use tap-to-record and tap-to-send, with a maximum 20-second recording. Recordings are sent for a single AI reply after Send or the recording limit. This implementation is turn-based, not a continuous full-duplex call. Replies are buffered, so there is a pause before playback.

For Chat and voice, visitors can switch modes and keep the recent request context. Voice-only sites hide the mode selector until the voice limit is reached, then offer chat. The final allowed voice reply finishes playing before fallback; chat then uses its separate allowance. A site that exhausts both allowances keeps its current view and ordinary browsing controls. **All of the site** restores the default view; catalog filtering, selection, comparison, detail and photo viewing do not consume AI attempts.

The dashboard preview always uses deterministic demo replies and, where available, an installed local device voice. It never requests a microphone or contacts OpenAI. Published sites on the local demo backend are also deterministic. Firebase sites require the existing OpenAI connection (`VOICE_AI_MODE=openai`); unavailable configuration fails closed. No environment, authentication, deployment, or billing settings are changed by this feature.

## Component selection and motion

For catalog sites, the model returns a strict ready/unavailable envelope containing a versioned `PresentationPlan`. The plan has a snapshot ID, operation, semantic transition and up to eight controlled components, one of each type. It references existing entities, typed attributes, collections, registered capabilities and approved media. Detail requires one entity; comparison requires two to six entities and at least one declared attribute. Provider instructions ask for useful shared attributes, but schema validity alone does not prove comparison quality. Unknown values remain unknown, and a photo or published schedule does not establish live availability or an executable action.

Both server and browser validate these references and compatible variants. The shared runtime then compiles the plan into local OpenUI grammar, performs bounded preflight/parsing and renders the platform's React components. It does not accept model-generated JSX, HTML, CSS, URLs or business facts, and it does not depend on OpenUI Gateway. Catalog selection remains runtime-owned. See [contracts](../packages/platform-ui/src/contracts.ts), [provider envelope validation](../lib/catalog-presentation.ts) and the [architecture](architecture.md).

The legacy path uses a smaller plan with a layout, up to six published source IDs and a ready/unavailable status, plus bounded references for approved galleries. Its comparisons show published descriptions rather than invented metrics. Both paths report unavailable information and preserve the accepted view when a plan cannot be supported.

Responses uses Structured Outputs to select the typed-request view. Realtime calls the display-only `present_site` function exactly once, then receives the validated selection for one spoken response with tools disabled. The function only prepares UI; it cannot edit, book, send, purchase, access accounts, or execute generated code. Invalid plans fail without a provider retry or a second voice generation. A cancelled, failed, stale or malformed response leaves the previous view intact. Manual interaction cancels pending requests so a late response cannot replace the visitor's newer view.

Suggested requests fill the composer and never send automatically. Enter submits, Shift+Enter adds a line, and composition input is respected. A progress indicator appears immediately; the selected components enter once a complete response has been validated. Failed or cancelled requests return to the composer. Recent requests and selected views provide bounded follow-up context across text and voice. All of the site clears that context and restores browsing without resetting usage. Changing draft content resets the preview view and any pending voice/request.

The shared motion vocabulary uses 480 ms reveal/disclosure, 560 ms reflow, 620 ms workspace/focus/restore and 400 ms exits. Stable component identities preserve existing controls while surrounding geometry changes; criteria expansion retains the first four controls. Exiting controls become inert immediately. Reduced motion removes movement and looping indicators. Requested destinations scroll into view only if offscreen after their layout settles, and visitor input cancels that pending reveal. See [shared motion](../packages/platform-ui/src/motion.tsx) and [browser regressions](../tests/browser/motion.spec.ts).

The owner preview and demo backend use deterministic matching to exercise the same renderer. Demo matching is not a semantic model and cannot establish live selection quality. Source documents must pass Knowledge review and publication before their semantic records appear publicly. Photos must be applied to the reviewed library and published. Uploading an original alone does not make it visitor content. The [three synthetic fixture catalogs](../fixtures/README.md) exercise the shared controls across different domains.

## Models and limits

| Path | Model | Bound |
| --- | --- | --- |
| Chat | `gpt-5.6-luna` via Responses | One request; 1,200 output tokens for a catalog plan or 700 for the legacy path; 30-second timeout |
| Standard voice | `gpt-realtime-2.1-mini` | One planning response (1,200 tokens for a catalog or 250 for the legacy path) + one spoken response (500 tokens) per server WebSocket |
| Premium voice | `gpt-realtime-2.1` | Same bounds, low reasoning effort |
| Voice input transcript | `gpt-4o-mini-transcribe` | Only the submitted voice recording |

Voice replies use `marin` with mono PCM16 at 24 kHz. The Standard/Premium selector changes the model, not the speaker's voice identity. A voice attempt has a 35-second deadline, a 20-second input limit, and a 30-second returned-audio limit. Transcription may finish independently of audio; the server waits up to two additional seconds within the same overall deadline for it. Missing input transcripts use “Voice request” in internal context. Greetings remain one response capped at 750 output tokens. Two-step catalog voice has a combined maximum of 1,700 output tokens; the legacy two-step path has 750. No provider retries occur automatically. [Provider implementation](../lib/visitor-provider.ts)

Per-site defaults when enabled are 25 chat attempts and 5 voice replies daily. Publishers can set 1–100 chat attempts and 0–20 voice replies. These are shared across all visitors to the site. The server also caps the entire deployment at 100 chat attempts and 20 voice replies per UTC day. Platform usage can therefore make a site reach its allowance sooner. Counts are separate from the owner's AI editor usage.

A greeting counts as a voice reply. Valid requests reserve usage before contacting the provider. Failed and cancelled attempts count; there are no refunds or automatic retries that could silently spend again. A UUID replay is rejected. Changing modes or quality, refreshing a page, or clearing a browser conversation does not reset server usage. These are attempt limits, not exact dollar budgets or subscription plans. Cost varies with input, output, model, and transcription.

## Storage and request boundary

`/api/visitor/[slug]` reads the published snapshot and selected model on the server. Clients cannot supply a model, tier, system instructions, or site content. The server checks the origin, message/history lengths, recording bytes and total request body size. Catalog state includes the snapshot, filters, selected IDs, focused ID and visible IDs; the server validates it against the publication before reserving an attempt and checks for a publication change at reservation. A process-local 120-request/minute gate limits traffic before storage access. It is not a distributed per-visitor abuse prevention system; anonymous visitors can consume a site's shared allowance.

Firebase usage is reserved transactionally in the server-only `voiceVisitorUsage/current` document, reading `voicePublished/{slug}` in the same transaction. The document keeps the UTC date, counters, and bounded request IDs; it does not store visitor messages or audio. The local demo uses the existing serialized file-store queue and an optional `visitorUsage` field. A corrupt or future-dated ledger fails closed. UTC rollover resets usage automatically, with no scheduler, trigger, or background job. The existing Firestore rules deny browser access; no rule changes are needed.

Server WebSockets are deliberately used instead of handing the browser an extensible provider session. Each socket generates at most one component-selection response and one spoken response, then terminates. No additional tool rounds are allowed. Greetings use one spoken response only. Keys remain server-only. Request cancellation, timeout, malformed output, and disconnects close the socket. Browser recording and playback stop on cancellation, mode changes, content changes, unmount, pagehide, or a hidden document. Late microphone permission results are stopped and discarded. Provider reply completion is separate from browser audio playback completion.

Request/view context is held in component memory (at most 8 messages, each truncated to 2000 characters for requests) and disappears on reload or All of the site. It is not rendered as a transcript. Catalog browsing also has its own bounded in-memory view history and shortlist; returning to All items preserves selections. Published content/catalog/media descriptions and submitted visitor messages/recordings go to OpenAI in connected mode. Responses requests use `store: false`; provider retention remains subject to the configured account's policies. The application does not persist visitor audio or conversation history. It records bounded operational events and measured provider usage, with IDs and counts rather than conversation text; see [platform events](../lib/platform-events.ts).

## Verification

Run `npm run check` using Node 24 for lint, types, persistent offline tests, the packed shared-package consumer and a production build. Then run `npm run test:browser` for a fresh headless Playwright context and isolated demo data on port 3225. These commands are defined in [package.json](../package.json) and [Playwright configuration](../playwright.config.ts).

The current tests cover contract/reference bounds, provider envelopes and bounded calls, draft/publication isolation, real OpenUI rendering, manual filtering/selection/comparison, stale and malformed mocked plans, cancelled late results, intermediate motion geometry, mobile/reduced-motion behavior and contextual photos. Provider and Firebase transports are mocked; local persistence and browser rendering are real. See [catalog provider tests](../tests/catalog-presentation.test.ts), [renderer tests](../tests/presentation/runtime.test.ts), [platform browser tests](../tests/browser/platform.spec.ts) and [photo runtime tests](../tests/browser/media-runtime.spec.ts).

Live model quality, real microphone/audio behavior and Firebase permissions require separate authorized verification. Offline tests do not prove production configuration or provider billing accuracy, and do not authorize paid calls or deployment.
