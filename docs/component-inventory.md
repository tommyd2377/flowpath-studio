# Current component inventory

**Work item 5 · audited September 19, 2026 against the working checkout, including uncommitted changes.** This is a code-grounded map for the backlog, not a new interface proposal or a claim of live acceptance. The [older proposal](component-interaction-system-proposal.md) remains historical design input; its component names and assignment-2 host description are not the current inventory.

## Current composition and selection boundaries

[SiteExperience](../components/SiteExperience.tsx) mounts the independent [WebsiteSurface](../components/WebsiteSurface.tsx) and [VisitorAssistant](../components/VisitorAssistant.tsx). The assistant keeps the website mounted and inert while [VisitorWorkspace](../components/VisitorWorkspace.tsx) composes **one evolving information surface**, using shared [InformationFrame / InformationRegion](../packages/platform-ui/src/InformationSurface.tsx). One primary and at most two supporting regions are visible. New primary content normally enters on the desktop right, retained context stays left, and mobile stacks content to conserve space, with retained video above its related answer. These are host layout rules, not model-generated coordinates. See [information-surface.md](information-surface.md) for the full lifecycle.

Three distinct selection contracts coexist:

## Prioritized gaps and decisions

1. **P1 — Close concrete coverage seams before adding component names.** Decide whether current visitor tasks need an explicit related-record/link region, and whether charts must cover v2 query results. Reuse the existing semantic records and comparison/chart renderers where their contracts fit. Verify the chosen path on at least two structurally different publishers, including unknown data, narrow screens and whole-state Back. This audit does not establish those integrations or authorize implementation.
2. **P1 — Annotated images, after publisher authoring is defined.** Useful across equipment parts, artwork details, venue plans and educational images. First define a bounded, versioned contract for exact asset/revision, normalized region geometry, stable annotation IDs, accessible labels, approved fact/entity links, actual/example meaning and private review evidence. Studio must support correction, review, Apply and Publish, plus invalidation/review when an image is replaced or cropped. Every region needs a keyboard/text-list equivalent and an image-unavailable fallback. Existing optional [web additions](../lib/explore-model.ts) attach external findings to a card; they are not this contract or pixel annotations.
3. **P2 — Interactive diagrams for one demonstrated cross-domain job.** Choose a bounded relationship/hierarchy or process view only after real tasks justify it. Missing authority: publisher-reviewed node/edge or step IDs, relationship meaning/direction, ordering, labels, qualified values and source/revision references. Missing authoring: correction/review, publication validation and a complete text/list/table alternative. Expansion/selection must join surface snapshots; mobile and reduced motion must preserve meaning. `DiagramPanel`, `DataStory`, `ImageFactMap`, `FactCluster`, `MultimodalCard` and `DecisionBoard` remain proposal names, not additional implemented registrations. Arbitrary generated SVG/HTML and a new canvas framework are unnecessary.
4. **P2 — Broader quantitative views only with approved inputs and rules.** Extend the narrow chart only for a demonstrated need. A reusable calculation requires approved operands, units/currency/basis, bounded formulas and ranges, rounding, missing/conflicting-value behavior, provenance and explicit calculated-result labeling. Review/publish the rule separately from visitor inputs; a calculated estimate must not imply a live quote or capability. A richer chart needs a correspondingly approved dataset/series contract. Source-document page viewing is a separate optional decision requiring an explicit public rendition/page/citation contract; current private upload evidence cannot be reused as visitor content.

Across these decisions, preserve one evolving surface and whole-state Back. When exact material is unavailable, the model should choose a useful supported alternative in context and explain the limit; a general gallery can sometimes help, but no missing-result case mandates a gallery or another fixed fallback. This is a composition policy, not a new component.
