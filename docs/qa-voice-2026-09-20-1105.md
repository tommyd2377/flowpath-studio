## 1. Photo collection exists in one tool's index but not the other's authority

The backend was explicitly given `published-photos` in its task collection index. It then used that ID as a collection reference in `update_workspace`, paired with the knowledge revision. That workspace validator only registers actual catalog collections, individual media assets and media albums. The generated task collection is not one of those workspace references.

This is an integration mismatch, not missing photos and not an ID invented without any input. The recorded failed action is sequence 523, followed by validation/task failure at 527–528. The regular website also exposes 57 non-logo photos.

Code: [task media collection construction](../packages/platform-ui/src/collection-space.ts), [workspace publication authority](../lib/visitor-workspace.ts), [workspace validation](../packages/platform-ui/src/workspace.ts).

**Required repair — PHOTO-ROUTING-04:** make the model's advertised references usable through the corresponding validated display route, or explicitly translate supported task references to authorized media references. Preserve current-publication validation. Return a distinguishable display failure so voice cannot turn a tool rejection into a claim that photos do not exist. Do not add a universal gallery fallback. Test all photos, named albums and filtered photos, including conflicting collection IDs and separate knowledge/media revisions, across unrelated publisher fixtures.

## 2. Menu selection is structurally wrong even when the facts are right

For “see a menu,” the model opened the narrative **Our Dessert Menu** entity, then read it with `record.detail`. That record contains flavor lists, price ranges, specials, catering and ordering paragraphs. The resulting wall of text comes from the selected representation, not a lack of structured products in the publication.

**Required repair — LAYOUT-01:** give browsing requests the relevant structured offering collection when one exists, with prices and related images. Keep source prose and ordering qualifications available as supporting detail. Apply this principle to services, courses and other domains; do not hardcode a cake-menu phrase or fabricate item prices from ranges. Include live-model routing acceptance separately from renderer-only tests.

## 3. Session expiry exposes a stale-restoration dead end

The connection starting at approximately 11:03:25 ended at its configured two-minute limit. The velvet request had already begun backend work but had not produced a confirmed replacement display.

On reconnect, the browser still reported task revision 19 / generation 4. It attempted to restore the saved menu state with generation 4 twice; both requests returned 409 and both preparation acknowledgements failed. Preparation failure correctly prevented model work against an unconfirmed view, but there was no recovery, so repeating the request could not help.

The code explains the stale-state path: [task bridge creation](../lib/visitor-task-bridge.ts) advances the task generation before model work, while [saved-view restoration](../components/VisitorTasks.tsx) sends its cached generation without refreshing it. The [task API](../app/api/visitor/[slug]/tasks/route.ts) rejects generation mismatches. The HTTP recorder does not retain the 409 response body here, so its exact server error string is not independently established; the recorded stale generation and inspected code identify the likely cause.

**Required repair — RETAINED-VIEW-03, reopened:** synchronize task metadata after expiry/cancellation and before restoring a retained view; handle a stale restore with a bounded, local resynchronization that still respects newer manual actions. Preserve the useful confirmed view and fresh visitor intent. Do not remove concurrency checks or retry paid model work automatically. Add a regression for expiry between acknowledged preparation and completed backend work, reconnect, two fresh requests, Back/Home and subsequent filtering. Raising the session limit is a separate product/cost decision, not required to fix recovery.

## 5. Regular website: priced-item layout makes photos enormous

The separate fresh preview uses Showcase, refined website design, balanced layout and Subtle motion, with neither paused nor reduced-motion mode active. The defect is reproducible in the current renderer; Motion being present does not make the underlying geometry correct.

At a 1,280 × 720 viewport:

- A priced collection becomes a single **1,152-pixel-wide column**.
- Its product image takes the full column width and a forced 4:3 aspect ratio: **1,152 × 864 pixels**.
- One cake card is approximately **1,051 pixels tall**. The unexpanded page is approximately **19,482 pixels tall**.
- The first item uses a 350 × 350 decorative source image, enlarged as a product image. Later assets include very wide decorative backgrounds.

The cause is explicit in the shared implementation. [Collection classification](../packages/platform-ui/src/PublishedWebsite.tsx) marks any section containing a price as `priced`. [Website CSS](../packages/platform-ui/src/website.css) then gives priced/service collections one full-width column. The card places its image above the text without a thumbnail bound. Showcase adds the 4:3 image ratio. The priced rule overrides the normal two-column Showcase collection layout.

The earlier hero-image bounds apply to hero figures, not these collection cards. The current website fixture gives menu images site/gallery associations but no priced-item image association; its entity-photo association is only on the portfolio fixture. That leaves this price-plus-photo combination uncovered by the existing visual cases. See [website fixtures](../tests/browser/website-fixtures.ts) and [hero checks](../tests/browser/website-hero.spec.ts).

There is also a test-content quality issue: the authorized “use all images with illustrative menu labels” setup includes decorative source assets. Those arbitrary assignments are correctly marked illustrative, but they also feed the regular website's product-image selection. That makes this fixture unsuitable as a polished visual demo without a separate curation pass. It must not be mistaken for verified photo identity.

The site's opening hierarchy repeats the business identity and places general business/location records before the retail cake collection. That is an additional composition concern; the massive product images are the directly measured defect. No missing hero-selection cause was established in this audit.

**Required repair — WEBSITE-PRICED-MEDIA-04:** design bounded photo-and-price rows or an appropriate responsive product grid in all three templates, with stable crops and a deliberate text-only variant. Cover priced products and services, mixed photos/no photos, small images and very wide assets on desktop/mobile. Verify actual image bounds and scroll density in the rendered browser, plus reduced motion and assistant return. Treat decorative-photo curation as a separate reversible test-data change; do not silently alter a publication.
