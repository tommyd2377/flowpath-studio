## Content and policy binding

`canonicalCreationCandidate()` retains the saved trim rules, 80-character name and 15,000-character instruction limits. It includes the optional Text Box configuration (v1 authored text or v2 capability), bounded server-normalized portrait, and optional immutable document binding `{id,digest,filename}`. Absent new fields are omitted to preserve existing text-only digest compatibility. No content is truncated. HTML-shaped text stays escaped text.

`creationContentDigest()` binds all reviewed content. Portrait uploads are normalized identically before review and save. Material edits and policy changes invalidate approval; voice/accent/adminTesting cannot grant it. A document has its own current-review pointer, so reviewing one file cannot replace waveform approval. File bindings are checked against current owner metadata inside protected transactions. Removed or changed files cannot use an old approval.

`CreationSafetyPolicy` requires an explicit action for every exported category. Local v3 routes material historical controversy and portrait provenance to the founder; all other categories block clear violations. Its hard identity rules exclude living people and people dead less than five years, using a server-provided UTC date/cutoff. Unknown dates require manual verification. Disclosed historical simulations are eligible for conversation or fun without a teaching requirement; ordinary historical complexity alone must not cause a flag. Production policy selection remains separately configured. Founder approval cannot override an already blocked result.

`CreationSafetyBinding` contains `{ digest, policyVersion, policyDigest }`. The policy digest includes the version and ordered category actions, so changing a category also invalidates approvals when the version was not bumped. Review findings must cover every category with `clear`, `violation` or `uncertain`. A violation of a blocking category blocks; another violation, uncertainty or malformed/incomplete findings require manual review. Only complete clear findings allow automated approval. Reviewer failures/unavailability require manual review.

## Server API and storage

`createCreationReviewStore(database, options)` consumes the existing `VoiceDatabase`/`VoiceTransaction`, not a parallel database abstraction. Options supply the policy, a production/fixture mode, optional trusted reviewer, clock and required owner/admin verification callbacks. Verification must use server-verified UID/session authority **inside the supplied transaction**; request bodies, role booleans and the founder admin-testing preference are not authority. This lane intentionally does not change auth schemas.

- `request(actor, candidate)` returns `{ record, needsReview }`. Identical current content/policy reuses its review, including pending or completed results. A material change creates a new current review; no old completion can replace it. Returning to an earlier completed **allowed** version reuses that exact owner/content/policy proof without another model call. The server checks the actual stored review and current document validity; a stale, revoked, changed or different-owner approval cannot be reused. This lets creators discard an unsaved draft without losing the saved version's approval.
- `runReview(proof)` claims one attempt outside the transaction, then rechecks content, policy and document validity on completion. The local adapter uses only `gpt-6-luna`; no client verdict, fallback or automatic paid retry is accepted.
- `get(actor)` returns that owner's current record after verification. It is private and contains the submitted prompt; integration must use an explicit minimal projection for browser status.
- `requireAllowed(tx, ownerUid, candidate, expectedBinding?)` recomputes the binding and reads the current allowed record in the caller's transaction. It returns the server proof or throws. Create/Save reuses this allowed review rather than making another model call. Missing legacy approval, pending, blocked, manual review, changed content/policy and a mismatched expected binding all fail closed.
- `listManual(actor)` requires verified review-admin authority and returns pending/manual candidates in the unresolved queue. Pending items are visible for operations but cannot yet receive a manual decision.
- `decide(actor, { ownerUid, reviewId, digest, policyVersion, policyDigest, decision })` requires verified review-admin authority and an exact current `manual-review` proof. An explicit allowed/blocked decision records actor UID and time, removes the item from the queue and is bound to that exact content/policy. It cannot override a category block, approve pending work, replay a decision, or approve a newer version.

Server-only collections are `creationSafetyOwners/{sha256(uid)}` (current review pointer), `creationSafetyReviews/{randomUUID}` (candidate, binding, state, attempt/decision metadata), and `creationSafetyQueue/manual` (unresolved review IDs). The queue contains at most 200 records and rejects additional work when full. A new version removes its superseded version from the queue. Completed historical records remain private for audit; retention/cleanup is undecided. No prompts, review content or provider errors are logged by these modules.

`creationSafetyVersions/{hash(uid,contentDigest,policyDigest)}` is a server-only index of genuine allowed reviews. An existing current approval is indexed transactionally when another draft replaces it, so existing records need no migration. Restoring it changes only moderation pointers, not saved waveform settings. Missing approvals never receive an exemption.

The store reads before writing, as required by Firestore transactions. Reuse the **same backing database and transaction** for safety and protected content/accounting mutations. Call `requireAllowed` before the mutation writes, and ensure every other transaction read also precedes writes. Publication/admission must independently check authoritative safety against the exact loaded snapshot inside their own transaction. A preflight check followed by a separate write/reservation is insufficient. Carry the returned binding with a saved snapshot so the loaded content and reservation cannot diverge after a concurrent edit. Safety failure must roll back the protected mutation/reservation.

## Fixtures, unavailable infrastructure and recovery

No reviewer defaults to allowing content. With configured policy but no reviewer, a claimed request becomes `manual-review` with `review-unavailable`; it cannot be used until an authorized exact-version human review completes. With missing or invalid policy, operations needing approval return unavailable. Production mode refuses to invoke a fixture reviewer, and fixture store mode is rejected when NODE_ENV is production. `createFixtureCreationReviewer({nodeEnv:'development',enabled:true}, callback)` additionally requires explicit development-fixture selection; its injected callback is synthetic evidence only.

After two minutes, the founder queue converts interrupted pending work to manual review without another model attempt. Failed, incomplete, refused or unavailable reviews fail closed. An older external attempt may finish after an edit, but cannot authorize the newer version. No new cloud jobs or resources are created. Review delivery is request-bound in this MVP; durable background jobs remain future work.

## Local operating budget and file coverage

The owner approved a **50¢ cumulative review budget per waveform**, shared across its name, instructions, portrait and documents (one waveform per owner today). `creation-review-budget.ts` reserves 5¢ atomically per bounded attempt and settles once. An uncertain outcome consumes the full 5¢ estimate, keeps that version manual, and is never refunded or automatically retried. A different version needs its own reservation within the same cumulative cap. Review spending uses separate server-only collections; it never grants customer credit, charges customers, uses analytics as authority or changes voice-testing quotas.

Before inference, `/responses/input_tokens` must report at most 90,000 input tokens; output is capped at 2,048. Accounting uses conservative rates of $0.50/M input and $0.75/M output plus $0.001 per attempt, covering the currently published Luna rate variants with schema headroom. These are internal estimates, not actual provider invoices or a provider-enforced spending cap. Pricing drift requires revalidation. Exhaustion routes to founder review without automatically increasing the budget.

PDF review includes text and page images. New TXT uploads review their complete original UTF-8 bytes during upload, verifying SHA-256 and retaining no extra original copy; indexing completion reuses that review. Existing TXT retrieval is attempted once and requires an exact byte hash; unavailable originals stay manual. DOCX goes to manual review because the API does not extract its embedded images. Oversized, unreadable or incompletely covered files also require manual review. The private founder queue offers original download, but the provider rejected retrieval of the acceptance TXT with HTTP 400. A founder must obtain and inspect a matching complete original before approving; broader manual-review storage/delivery needs a hosted design. Portrait review does not identify faces; unverified human likenesses require manual review.

New/changed editor drafts review after a short debounce. Opening unchanged saved settings only reads status; **Review this version** starts the initial review or retrieves an existing decision. Save never starts a redundant review. Existing Knowledge is shown as review-required without silently starting paid work; **Review document safety** explicitly reviews it. New uploads progress from indexing through review, and cannot be selected/searched before approval.
