# GPT-Live voice architecture

Studio and the independent FlowPath app maintain copies of `lib/gpt-live/{protocol,backend,runtime,browser}.ts` that are intended to stay identical. Each repository builds independently; `tests/gpt-live.test.ts` compares these files byte for byte when both sibling checkouts are available. Changes to the common core must be reconciled in both repositories. Product content and tool adapters remain app-specific. **September 20:** local sibling parity was already failing before this repair; Studio's optional listening-only startup is also pending reconciliation in the separate FlowPath checkout. Do not claim current byte parity.

## September 20: current visibility and reconnect readiness

Studio starts visitor-first and resumed calls with `start('listen')`. It sends the silent-readiness instruction before enabling delegation; retained history alone does not trigger backend work. User transcript fragments received during startup remain eligible. This avoids the previous intermediate instruction inviting a response before the host's silent-resume policy. Actual audible compliance and interruption still require a recorded microphone test.

Screen visibility now travels as one compact observation: primary/supporting region, visible/offscreen state, observed item count, short labels and history availability. Full validated references remain in the delegated backend context. Photo labels for at most four visible images use their own context channel; paging no longer retransmits unchanged answers or contact facts. Published content and conversation research remain independent of current visibility. An append acknowledgment confirms delivery, not model comprehension; this follows the [Live context model](https://developers.openai.com/api/docs/guides/live-conversations).

The browser confirms visible requested regions and loaded gallery/photo content before returning display success. Clarification uses its own empty record receipt, not IDs from retained detail. A cancelled task's server generation can advance while its old view stays visible; preparation checks that generation and restores with fresh metadata. Restoration does not replay paid tools. See [recorded evidence and verification](qa-voice-2026-09-20-fixes.md).

## Shared path

Browser microphone and speaker → audio-only WebRTC → GPT-Live-1 (Marin). The application server creates the session with `POST /v1/live/sessions`, reads the JSON session ID and SDP answer, and attaches to `/v1/live/sessions/{id}/attach`. The browser has no provider command channel or provider credentials. Browser media readiness precedes the opening message. ICE gathering completes before the offer is submitted.

GPT-Live uses client delegation. The server accumulates exact timestamped transcript fragments and supplies those plus current validated application state to GPT-5.6 Luna through Responses. Delegation events carry an opaque ID, not task text. Transcript gaps never trigger tools. The shared runtime cancels on a new accepted delegation or explicit app interruption; Studio applies the conversation policy below before accepting a delegation. Context is ephemeral and bounded. The common backend and Studio's task runner have no automatic retries or parallel tools and permit at most four tool rounds followed by one tool-free response. Initial output is capped at 1,200 tokens and continuations at 500. Each delegated job has a 35-second deadline, including when a backend ignores abort.

Only app adapters execute tools. Studio validates published references and waits for browser acknowledgments for plans, navigation and external search views. FlowPath retains its news attribution, story selection, path, research and screen handlers. Large catalogs and research stay in backend context. Speakable results return through `session.commentary.append`; context and application instructions use their separate append events. Every append is conservatively bounded to at most 480 UTF-8 bytes, below the 500-token API ceiling.

## Studio interruption ownership

The September 13 regression reproduced a pending backend answer surviving new spoken Home/cancel instructions when Live had not yet emitted another delegation. Since backend work and Live speech have separate lifetimes, stopping speech alone did not stop the job; it could return near the 35-second deadline. This reproduces a possible cause of the reported delayed answer, not a diagnosis from a recorded live session.

`lib/visitor-realtime-control.ts` keeps pending work during ordinary conversation. A 350 ms gap groups captions but cannot cancel a task by itself. `visitor-voice-input.ts` recognizes narrow explicit cancellation, navigation and correction hints that invalidate old work before the next delegation. Other substantive new requests replace work when Live delegates them. Status questions, acknowledgements, “keep working while we talk” and “stop talking” do not restart or cancel the task even if Live delegates them accidentally. Stopping speech only asks Live to listen. These English control hints are bounded heuristics, not authoritative turn detection or general semantic classification; other languages and ambiguous corrections depend on Live delegation. No transcript directly executes a website action.

Manual changes cancel before publication-check I/O; `lib/visitor-realtime-session.ts` forwards the cancellation hint even while an earlier queued context update is still waiting. Applying a view still requires publication authorization. An input-version fence prevents a late delegation containing only pre-cancellation speech or acknowledgements from restarting the old task. Every navigation/plan waiter has an abort listener and its own identity, and every delegated job captures its own task bridge. Late provider results, errors, usage attribution and finalization cannot be assigned to a newer bridge. Cancelled interpreting tasks are marked cancelled without changing other tasks. Provider-level usage already incurred remains recorded.

`response_cancelled` tells `lib/use-visitor-session.ts` to abort old motion, clear obsolete activity and mute output while retaining the microphone and call. Playback resumes only after both observed output quiet and an owner acknowledgement at or beyond the cancellation revision. An acknowledgement alone is not playback completion. The existing output-quiet observation remains a heuristic; WebRTC provides no per-answer audio identifier here, so this does not prove that every possible delayed audio packet has been drained. New request revisions also invalidate old browser navigation promises. Diagnostics record cancellation/revision metadata without logging transcript text.

Regression coverage in `tests/visitor-realtime-control.test.ts`, `tests/visitor-task-integration.test.ts` and `tests/browser/visitor-realtime.spec.ts` exercises spoken redirection before delegation, backchannels, overlap, manual cancellation during slow authorization, late delegations, abort-ignoring search results, old navigation timers/ACKs, model preparation cancellation, task ownership, and browser output/ACK ordering. These use synthetic providers and audio; real speech timing, recognition quality and device playback still need a bounded live test.

## Responsiveness and background conversation (September 15)

- The browser's `working` state belongs to the accepted request revision. Audio input, output and playback captions cannot clear it. Completion, failure, cancellation, manual interaction or End can clear it; stale completion events cannot clear newer work. The floating status remains visible during listening and speaking, with search and view-update labels when those operations run. The inactivity timer also stays busy through background work.
- Accepted work sends quiet progress to Live immediately. After 350 ms, a still-pending request sends one brief spoken acknowledgment unless Live has already supplied a new assistant caption. This delay avoids extra chatter for fast results; the caption check only suppresses duplicates and does not prove playback. Subsequent step changes supply concise, application-authored progress. Cancellation and deadlines suppress late progress along with late results.
- `visitor-response-connection.ts` lazily opens one Responses WebSocket for a voice session's first authorized backend call. Tool continuations reuse it with the actual prior response ID and only the new input when the cached context matches. Fresh jobs carry their full bounded context. Cancellation, errors and disconnects discard that connection's cache; a fresh request can connect again. There are no speculative requests, paid warmups, automatic retries, transport fallback retries or parallel model jobs. Chat and injected offline providers retain their existing HTTP path through the same task runner.
- Streaming text and tool deltas record time to first model output. They cannot execute tools, become spoken success or leak private reasoning. Only a complete validated response executes a tool; only a browser-acknowledged action can be described as applied. Progress can reach Live while that work is pending.
- A whole, simple navigation request can return a deterministic confirmation after the browser ACK, skipping the closing model call. Exact names and existing page intents bound this shortcut. Compound requests and requests for explanations continue through the shared executor and current-view refresh. Failed navigation cannot produce a success confirmation.
- Focus/return travel uses 520 ms rather than 800 ms. The non-catalog Browse path retains stable-layout checks with a 120 ms floor rather than an 850 ms floor. Browser acknowledgments still require the correct committed view and completed focus return. Reduced motion and manual interruption remain supported.

Diagnostics distinguish `acknowledgment` submission, each `model` request, first `model_output`, confirmed `navigation`, and the final backend `result`. Browser `turn_audio` measures the first observed unmuted output onset following the request-start event; it may be an acknowledgment or conversation, not the useful answer. Server and browser use their own monotonic durations with matching revisions. These measurements do not establish end-to-end spoken latency or whether the visitor heard a useful answer; a separately authorized audio evaluation is required for that.

Regression tests use synthetic delayed responses, fragmented WebSocket events, status questions, explicit cancellation, stale frames, timeouts, compound navigation and browser audio levels. The browser tests verify persistent status on desktop/mobile and the real local typed panel lifecycle. These checks establish local control behavior, not live model routing, provider WebSocket availability or acoustic turn-taking quality.

The final status-placement change passed a fresh lint/build and both browser status cases. All 31 voice browser cases passed; both typed panel-lifecycle cases passed, including keyboard focus return and mobile reduced motion. The sibling FlowPath core passed its 14 tests. Three additional catalog cases in `tests/browser/adaptive-workspace.spec.ts` still fail their initial workspace-card count assertions before reaching motion: the current website-query flow handles those requests in the website view (the address search returns no matching items). ## Audio and lifecycle

Input, output and backend activity remain independent. Waveforms and the shared optional startup protection use browser media levels, not transcript arrivals, backend completion or append acknowledgments. The shared guard keeps original microphone capture running and can mute cloned outgoing tracks during an iOS opening; protection ends two seconds after first observed output activity, with a ten-second no-output escape. Studio no longer enables that opening mute: its outgoing tracks become available after the readiness acknowledgment and stay available during the greeting. The shared implementation and the independent FlowPath app remain unchanged. Microphone initialization and acoustic echo cancellation still belong to the browser; physical mobile echo and interruption remain separate acceptance checks.

Output quiet uses a 1.2-second observation window. This is a UI heuristic, not proof a sentence finished or that a user heard it. FlowPath uses it to advance its per-card briefing; long within-sentence pauses may need real-device tuning. Studio does not put generated assistant transcripts into cross-mode history as fully heard answers. User caption grouping is revisable; the backend keeps original fragments during the active session.

End requests `session.close`, keeps the sideband receiver alive, and awaits `session.closed` before releasing resources. A bounded timeout retains the latest duration as unconfirmed and invokes the hangup fallback. A successful HTTP hangup is not proof of final usage. Session duration snapshots are cumulative, never summed; backend token usage is separate. Existing app session-duration limits remain: Studio 120 seconds; FlowPath 600 seconds locally or 270 seconds on its hosted transport. These app limits do not create different voice quality tiers.

Both apps also use the shared inactivity policy. A session stays open while visitor input, assistant playback or backend work is active; after the configured quiet period the browser and server close the Live session. Studio publishers choose 30 seconds, one minute, two minutes or Never, with one minute as the default. The server remains authoritative so a backgrounded tab cannot leave a silent session charging. Tapping the waveform after an inactivity close starts a new session with the current bounded context.

## Studio pause and restart follow-up (September 13)

Two deterministic regressions reproduced old work surviving a quiet period: a new delegation ID could repeat a completed or failed request after 45 seconds without fresh speech, and repeated quiet audio/context reports could postpone the inactivity deadline. These are reproduced failure paths, not a recording-based diagnosis of the user's live session.

- `lib/visitor-realtime-control.ts` consumes the transcript versions belonging to completed and failed requests as well as cancelled requests. Overlapping trailing captions belong to the same request. A late delegation or acknowledgement alone cannot repeat that work or reserve another backend turn; fresh substantive speech still can. Rejected stale delegations emit bounded diagnostic metadata, without replaying results, showing Thinking, or resetting inactivity.
- Server audio reports only update the idle timer when input/output activity changes. `lib/use-visitor-session.ts` starts its idle timer once at readiness and changes backend activity only on transitions. Repeated owner acknowledgements, rendering and idle events do not restart its quiet deadline. Actual audio/backend work still keeps the session open under the existing publisher-selected timeout and hard session limit.
- `lib/visitor-realtime-session.ts` starts the voice model with empty message input rather than replaying old questions as input. The resumed controller supplies bounded earlier dialogue through reference-only thinking messages and explicitly waits for fresh speech; the backend retains the full bounded history separately from `latestRequest`. Restarting keeps the actual current view. It does not clear cards, automatically replay an answer, reissue a task, or add a paid retry. An explicit new request drives subsequent actions through the same validated/acknowledged navigation path.

Regression cases cover 45-second pauses after success/failure, backchannels, trailing captions, quiet snapshots, inactivity despite rejected late delegations, and browser inactivity close → restart with the same foreground card → new Home request. Audio, provider events and backend replies are mocked; real recognition and provider speech behavior remain unverified. The existing speech/output-quiet heuristic limitations above still apply.

## Publisher defaults and compatibility

Before opening paid voice, `VisitorTasksProvider.settle()` prepares the current publication's task session. Legacy entity kinds, relationship kinds and money units are descriptive labels; `adaptV1Catalog` converts them to valid, distinct task identifiers without changing published record IDs or source data. Compatible existing IDs remain unchanged; fallback IDs are deterministic within an immutable snapshot and independent of record order. Whitespace, punctuation, Unicode and encoding collisions must not block this preflight.

Task initialization emits bounded browser diagnostics under `stage: context`, `operation: workspace`, with timing, status and HTTP classification. It logs no content or raw error bodies. A failed preflight reports the API's public error in the voice UI and stops before microphone/provider startup; retry remains an explicit visitor action. Regression coverage lives in `tests/visitor-hierarchy.test.ts` and the legacy startup case in `tests/browser/visitor-realtime.spec.ts`.

The 2026-09-13 fix passed `npm run check` (422 server tests, 21 rendering tests, package consumer and build) and two isolated browser regressions for startup and shared chat/voice task state. The local GoSite task initialization endpoint changed from a schema error to a successful session. Audio/provider calls in browser tests were mocked; no paid voice session was started for this verification.

Every new Studio publisher defaults to voice using GPT-Live. Both legacy saved Standard and Premium values resolve to GPT-Live-1; their obsolete quality picker has been removed. Publisher tone, content, greeting and voice/chat choices remain configurable. The legacy recorded-turn provider returns 410 and asks callers to reconnect using the continuous session endpoint. The offline publisher preview remains deterministic and does not call a provider.

Studio's **End voice after inactivity** setting defaults to one minute and is persisted with the published visitor configuration. Existing saved settings without the field resolve to that default when read. `Never` is available for publishers who want the existing hard session cap to remain the only automatic boundary.

Studio's daily voice allowance now bounds session starts/openings and delegated backend tasks, not individual sentences spoken by the continuous frontend. Independent hard session limits bound voice duration, including small talk and silence. Live duration and Luna token observations are operational measurements; they are not Stripe charges or reconciled monetary balances. The synthetic billing ledger and Stripe test controls remain separate and do not authorize live AI calls.
