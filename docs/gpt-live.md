# GPT-Live voice architecture

Studio and the independent FlowPath app maintain standalone copies of `lib/gpt-live/{protocol,backend,runtime,browser}.ts`. Each repository builds independently; `tests/gpt-live.test.ts` currently reports byte differences when both sibling checkouts are available. Product content and tool adapters remain app-specific. **September 27:** Studio now selects GPT-6 Astra/high for delegated work and permits direct Live general answers. This migration is scoped to Studio; the separate FlowPath checkout was not changed. Sibling parity was already failing before this migration, including Studio's listening-only startup. Reconcile intentionally in a separate authorized task; do not claim current byte parity.

## September 27: Astra backend and selective Live delegation

The standalone protocol exports `LIVE_BACKEND_MODEL = 'gpt-6-astra'` and `LIVE_BACKEND_REASONING_EFFORT = 'high'`. Studio derives its shared application model policy from these constants. The generic `runLiveBackend` uses Standard processing (`service_tier: 'default'`) and keeps the Responses endpoint, `store: false`, encrypted reasoning continuation, sequential tools, bounded rounds and no automatic retries. Every request, including the final tool-free answer, has an 8,192-token ceiling so reasoning does not crowd out the visible response; the spoken response remains short. This is a maximum, not a usage target or a measured speed improvement. High reasoning can take longer and cost more per delegated call.

Live may answer straightforward general questions and stable concepts directly, answer from current server-supplied published facts without a new lookup, and explain or repeat a still-current confirmed result with its scope and qualifications intact. Published facts do not need to be visible or previously returned by a backend call to be usable. Live does not refuse merely because a general subject is absent from the publisher's site. It delegates unconfirmed publisher facts, careful reasoning, calculations, multi-step synthesis, current or uncertain research, and screen changes. General background cannot establish the publisher's prices, hours, policies, availability or capabilities; retained dialogue alone is not evidence. Selection references come from the latest confirmed view, and success claims still require browser acknowledgment. The same policy applies across publisher domains, while publisher search permissions remain authoritative.

At startup, a developer `input_text` message carries the **Published website knowledge snapshot**. Since September 28, additional whole records can use spare space in `session.instructions`, inside a separately labelled untrusted JSON reference block; the trusted policy and publisher role remain verbatim. The complete input is bounded to **7,680 UTF-8 bytes** and the complete instructions (policy, role, notice and reference data together) to **15,872 bytes**. These conservative bounds leave framing headroom below Live’s independently documented 8,192-input-token and 16,384-instruction-token limits. They are **not exact token counts**: no supported Live tokenizer/count endpoint is documented, and the Responses token counter is not assumed to support Live. No startup inference or counting request was added.

Knowledge selection prioritizes identity, contact/hours and publisher-selected opening references, then interleaves whole prose, offerings, collection structure and media. Catalog records are balanced across categories and ungrouped types; large groups are sampled across their full range. V2 still hydrates at most **48 complete records in one authorized repository call**, rather than the first 48 index entries. A compact topic/category/media directory points to details that need lookup. Collections/albums with more than 48 membership IDs stay as directory pointers so opaque lists cannot crowd out facts. Directory counts describe **direct membership**, not descendant totals; pointers never count as complete knowledge. The input reports exact admitted/omitted record counts across both reference parts. Missing catalog/media data and partial coverage stay explicit.

Qualified or competing assertions and complete prose records stay together; a record too large for either field is omitted rather than clipped or automatically summarized. Approved media labels and transcript intervals remain reference data, not proof of visual identity. Missing facts still delegate. This is the session publication at its timestamp, not an ongoing bulk context stream or an invitation to speak. `knowledge_ready` and `voice.knowledge_coverage` record preparation time, per-field byte use, reference bytes, included/omitted counts and directory coverage. Late recorder attachment receives those numerical metrics too. See [capacity verification](qa-voice-priming-capacity-2026-09-28.md) for measured coverage gains and the remaining live startup/answer-quality check.

The publisher's ongoing assistant role is independently editable under **The Voice → Assistant role → Role and identity**. It reuses the existing `visitor.assistantPurpose` setting and is quoted by the same role builder in chat and Live instructions. It does not grant credentials, facts or capabilities. Welcome wording and up to three opening topics remain separate; changing them does not change the role. Saving updates the draft, while publication is still a separate action.

Both channels explicitly answer identity/purpose questions from that role in first person, and repeat the quoted role accurately if asked to recite it. They identify as the website's AI assistant, rather than claiming to be its human owner. This needs no lookup or delegation. With no role configured, the same default website-guide role applies to both channels. Prompt/request tests verify these instructions reach both paths and that greeting edits cannot replace the role; actual model wording remains a live acceptance check.

Direct answers can bypass tools, so the existing heartbeat also revalidates the session's publication every 15 seconds, with one check in flight. A changed or unverifiable publication closes the old conversation through the existing cleanup path; reconnecting loads current knowledge. This bounds stale startup context; it is not instantaneous validation of each spoken word. No new model call or paid retry is involved. Studio's delegated-voice deadline is now 90 seconds to accommodate Astra/high while preserving cancellation; this ceiling is not an acceptable latency target. Connected Studio request builders also use a 90-second transport timeout, while the existing chat task lifetime remains separately bounded. See [migration and priming verification](qa-astra-priming-2026-09-27.md).

The default and Studio override follow the official [Live prompting structure](https://developers.openai.com/api/docs/guides/live-prompting). [Astra migration guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra) supports the selected reasoning effort through Responses. Policy/request tests use synthetic providers; they verify configuration and grounding instructions, not model comprehension or actual spoken quality.

## September 20: current visibility and reconnect readiness

Studio starts visitor-first and resumed calls with `start('listen')`. It sends the silent-readiness instruction before enabling delegation; retained history alone does not trigger backend work. User transcript fragments received during startup remain eligible. This avoids the previous intermediate instruction inviting a response before the host's silent-resume policy. Actual audible compliance and interruption still require a recorded microphone test.

Screen visibility now travels as one compact observation: primary/supporting region, visible/offscreen state, observed item count, short labels and history availability. Full validated references remain in the delegated backend context. Photo labels for at most four visible images use their own context channel; paging no longer retransmits unchanged answers or contact facts. Published content and conversation research remain independent of current visibility. An append acknowledgment confirms delivery, not model comprehension; this follows the [Live context model](https://developers.openai.com/api/docs/guides/live-conversations).

The browser confirms visible requested regions and loaded gallery/photo content before returning display success. Clarification uses its own empty record receipt, not IDs from retained detail. A cancelled task's server generation can advance while its old view stays visible; preparation checks that generation and restores with fresh metadata. Restoration does not replay paid tools. See [recorded evidence and verification](qa-voice-2026-09-20-fixes.md).

## Shared path

Browser microphone and speaker → audio-only WebRTC → GPT-Live-1 (Marin). The application server creates the session with `POST /v1/live/sessions`, reads the JSON session ID and SDP answer, and attaches to `/v1/live/sessions/{id}/attach`. The browser has no provider command channel or provider credentials. Browser media readiness precedes the opening message. ICE gathering completes before the offer is submitted.

GPT-Live uses client delegation. The server accumulates exact timestamped transcript fragments and supplies those plus current validated application state to GPT-6 Astra/high through Responses. Delegation events carry an opaque ID, not task text. A transcript gap alone never executes tools. Studio also has the bounded explicit-request recovery described below when Live fails to delegate. The shared runtime cancels on a new accepted delegation or explicit app interruption; Studio applies the conversation policy below before accepting a delegation. Context is ephemeral and bounded. The common backend and Studio's task runner have no automatic retries or parallel tools and permit at most four tool rounds followed by one tool-free response. Output ceilings are 8,192 tokens per request, including reasoning. The standalone runtime retains its 35-second default; Studio's caller selects its bounded application deadline. Cancellation remains immediate even if a backend ignores abort.

## Recorded missing handoffs and premature speech (September 24)

Three user-selected recordings showed requests being heard and acknowledged without any `session.delegation.created` event or application action. See [the recording audit and verification](qa-voice-2026-09-24-handoffs.md).

- Native delegation remains the primary path. As of September 27, a bounded English request recognizer can recover an explicit display, research, calculation or action request after 1.8 seconds without another caption, only when input is quiet and no backend job is active. Plain factual questions no longer force recovery: Live can answer from published context or general knowledge and still delegate semantically when needed. It retains unfinished phrases across a pause, including “open up the … [name]”. It does not synthesize provider IDs: application-initiated work uses `delegation_id: null` through the same validated, quota-reserved, cancellable runtime. A failed, completed, cancelled or already-owned input cannot trigger another job. Status, quiet, cancellation, backchannels and unrelated conversation do not initiate recovery. This is a heuristic recovery path, not authoritative endpoint detection or a substitute for semantic interpretation.
- `request_pending` and `response_started` hold browser output while the first validated result is pending; the microphone remains enabled. `result_ready` releases it after the existing verified-result path (a factual result can precede its optional display; a display confirmation still needs its receipt). Failure/cancellation use their existing recovery paths. Progress remains visible. This gate also holds the earlier 350 ms spoken acknowledgment: delivery to Live is no longer a promise that a pending-work acknowledgment is audible. WebRTC audio has no per-answer identity, so model captions, gate tests and quiet observations cannot establish exact audible wording or eliminate every possible late audio packet.
- Visitor-first and resumed sessions keep output muted until fresh substantive speech, and apply the existing quiet-output drain. Following the September 27 memory fix, Live receives the accepted completed-history prefix once per connection, within the existing 32-message / 24 KB history bounds. This preserves earlier assumptions and later corrections; quoted dialogue does not establish verified facts. A trailing unfinished request is not reintroduced as pending work. No additional model round or history acknowledgment wait is added. Longer reconnect context can affect startup cost/latency; physical-phone impact has not been measured. See [verification](qa-context-rounds-speed-2026-09-27.md#subsequent-resumed-voice-memory-fix).
- Full catalog facts and research stay in the backend and recorder. Live receives bounded whole facts and a bounded recall directory, with current visibility and relevant research ahead of longer prose. Large answers are omitted with recall information rather than cut before their qualifications. A status question refreshes the model with actual application busy/idle state even if it does not delegate.
- The 120-second Studio session limit, publisher quotas, task deadlines and no-paid-retry rule are unchanged. Expiry retains the view and asks the visitor to tap to continue. Shared runtime parity with the separate FlowPath checkout remains a pre-existing reconciliation item; this change does not update that other app.

The protocol follows the official [Live delegation guide](https://developers.openai.com/api/docs/guides/live-delegation) and [Live prompting guide](https://developers.openai.com/api/docs/guides/live-prompting). Offline tests establish application behavior, not live provider interpretation, exact speech or acoustic interruption quality.

Only app adapters execute tools. Studio validates published references and waits for browser acknowledgments for plans, navigation and external search views. FlowPath retains its news attribution, story selection, path, research and screen handlers. Large catalogs and research stay in backend context. Speakable results return through `session.commentary.append`; context and application instructions use their separate append events. Every append is conservatively bounded to at most 480 UTF-8 bytes, below the 500-token API ceiling.

## Studio interruption ownership

The September 13 regression reproduced a pending backend answer surviving new spoken Home/cancel instructions when Live had not yet emitted another delegation. Since backend work and Live speech have separate lifetimes, stopping speech alone did not stop the job; it could return near the 35-second deadline. This reproduces a possible cause of the reported delayed answer, not a diagnosis from a recorded live session.

`lib/visitor-realtime-control.ts` keeps pending work during ordinary conversation. A 350 ms gap groups captions but cannot cancel a task by itself. `visitor-voice-input.ts` recognizes narrow explicit cancellation, navigation and correction hints that invalidate old work before the next delegation. Other substantive new requests replace work when Live delegates them; the quiet recovery path below can also hand off a fresh explicit request if delegation is delayed. Status questions, acknowledgements, “keep working while we talk” and “stop talking” do not restart or cancel the task even if Live delegates them accidentally. Stopping speech only asks Live to listen. These English control hints are bounded heuristics, not authoritative turn detection or general semantic classification; other languages and ambiguous corrections depend on Live delegation. No transcript directly executes a website action.

Manual changes cancel before publication-check I/O; `lib/visitor-realtime-session.ts` forwards the cancellation hint even while an earlier queued context update is still waiting. Applying a view still requires publication authorization. An input-version fence prevents a late delegation containing only pre-cancellation speech or acknowledgements from restarting the old task. Every navigation/plan waiter has an abort listener and its own identity, and every delegated job captures its own task bridge. Late provider results, errors, usage attribution and finalization cannot be assigned to a newer bridge. Cancelled interpreting tasks are marked cancelled without changing other tasks. Provider-level usage already incurred remains recorded.

`response_cancelled` tells `lib/use-visitor-session.ts` to abort old motion, clear obsolete activity and mute output while retaining the microphone and call. Playback resumes only after both observed output quiet and an owner acknowledgement at or beyond the cancellation revision. An acknowledgement alone is not playback completion. The existing output-quiet observation remains a heuristic; WebRTC provides no per-answer audio identifier here, so this does not prove that every possible delayed audio packet has been drained. New request revisions also invalidate old browser navigation promises. Diagnostics record cancellation/revision metadata without logging transcript text.

Regression coverage in `tests/visitor-realtime-control.test.ts`, `tests/visitor-task-integration.test.ts` and `tests/browser/visitor-realtime.spec.ts` exercises spoken redirection before delegation, backchannels, overlap, manual cancellation during slow authorization, late delegations, abort-ignoring search results, old navigation timers/ACKs, model preparation cancellation, task ownership, and browser output/ACK ordering. These use synthetic providers and audio; real speech timing, recognition quality and device playback still need a bounded live test.

### Fresh-request recovery and refinements (September 27)

The recovery timer waits for 1.8 seconds without a new caption and for reported microphone activity to be quiet. A fresh explicit request can then enter the same accepted-delegation path even when older work is still running. Previously, recovery waited for that work to finish, which could delay a correction for the entire backend timeout. Recovery still consumes each input once, uses the normal quota/authorization path, and never retries a failed request. A late provider delegation cannot start the recovered request again. The shared runtime's replacement option is opt-in; callers that do not request it retain the previous idle-only behavior.

Distinct complete requests are retained separately instead of concatenated into a single command. The backend receives `latestRequest` and at most three earlier requests of at most 2,000 characters each in `unfinishedRequestContext`. Those earlier requests are reference context for refinements such as “also include…” or “only those…”; they are not a backlog, completion evidence, or factual authority. The model decides which constraints remain relevant and an unrelated new request replaces earlier work. Pending refinements use the semantic backend rather than an isolated command shortcut. An incomplete phrase still survives pauses, overlapping trailing captions belong to the accepted request, and status/quiet/backchannel speech cannot erase a waiting refinement.

The local recorder adds content-free `voice.delegation_accepted` and `voice.handoff_recovered` metadata with input/revision identity and replacement/context counts. Operational diagnostics retain classified schema/reference errors from the original exception, and unacknowledged task/final-answer displays have a `display` reason. Invalid workspace batches remain atomic and do not launch a paid repair call. Synthetic cases matching the reported error categories are not a reconstruction of the unrecorded phone session.

Offline regressions cover busy A → B → refinement C, multiple requests before first handoff, incomplete and active-microphone speech, quiet/status/backchannels, duplicate overlapping/provider handoffs, stale results, invalid second workspace operations and failed final-answer display receipts. No paid calls or physical microphone tests are included in this verification; real recognition, semantic interpretation and iPhone audio timing still require a consented recorded session.

Display settlement observes the information frame, regions and grid items after their registered Motion animations complete; it requires three stable geometry/opacity frames instead of a universal quiet-period delay. Interrupted layout projection can finish without a prop completion callback. That recovery waits for the declared transition duration plus 80 ms, stable geometry, and no running or pending native animations before retiring an unmatched start. This is deliberately conservative: an unrelated infinite CSS animation in the same frame can prevent recovery and reach the existing display timeout. It does not fabricate a successful receipt or start a retry. Browser regressions cover reduced-motion paint, interrupted resize, replacement and Back/Forward; physical iPhone timing remains a separate check.

Reduced-motion navigation acknowledged within 300 ms of controlled browser-clock advancement after preparation; this is a regression bound, not a measured live/model latency. Ordinary replacement/history and task-gallery receipts were captured only with settled, opaque, unprojected content. Provider and microphone behavior were mocked; no paid call was made by this suite.

## Responsiveness and background conversation (September 15)

- The browser's `working` state belongs to the accepted request revision. Audio input, output and playback captions cannot clear it. Completion, failure, cancellation, manual interaction or End can clear it; stale completion events cannot clear newer work. The floating status remains visible during listening and speaking, with search and view-update labels when those operations run. The inactivity timer also stays busy through background work.
- Accepted work sends quiet progress to Live immediately. After 350 ms, a still-pending request sends one brief spoken acknowledgment unless Live has already supplied a new assistant caption. This delay avoids extra chatter for fast results; the caption check only suppresses duplicates and does not prove playback. Subsequent step changes supply concise, application-authored progress. Cancellation and deadlines suppress late progress along with late results.
- `visitor-response-connection.ts` lazily opens one Responses WebSocket for a voice session's first authorized backend call. Tool continuations reuse it with the actual prior response ID and only the new input when the cached context matches. Fresh jobs carry their full bounded context. Cancellation, errors and disconnects discard that connection's cache; a fresh request can connect again. There are no speculative requests, paid warmups, automatic retries, transport fallback retries or parallel model jobs. Chat and injected offline providers retain their existing HTTP path through the same task runner.
- Streaming text and tool deltas record time to first model output. They cannot execute tools, become spoken success or leak private reasoning. Only a complete validated response executes a tool; only a browser-acknowledged action can be described as applied. Progress can reach Live while that work is pending.
- A whole, simple navigation request can return a deterministic confirmation after the browser ACK, skipping the closing model call. Exact names and existing page intents bound this shortcut. Compound requests and requests for explanations continue through the shared executor and current-view refresh. Failed navigation cannot produce a success confirmation.
- Focus/return travel uses 520 ms rather than 800 ms. The non-catalog Browse path retains stable-layout checks with a 120 ms floor rather than an 850 ms floor. Browser acknowledgments still require the correct committed view and completed focus return. Reduced motion and manual interruption remain supported.

Diagnostics distinguish `acknowledgment` submission, each `model` request, first `model_output`, confirmed `navigation`, and the final backend `result`. Browser `turn_audio` measures the first observed unmuted output onset following the request-start event; it may be an acknowledgment or conversation, not the useful answer. Server and browser use their own monotonic durations with matching revisions. These measurements do not establish end-to-end spoken latency or whether the visitor heard a useful answer; a separately authorized audio evaluation is required for that.

Regression tests use synthetic delayed responses, fragmented WebSocket events, status questions, explicit cancellation, stale frames, timeouts, compound navigation and browser audio levels. The browser tests verify persistent status on desktop/mobile and the real local typed panel lifecycle. These checks establish local control behavior, not live model routing, provider WebSocket availability or acoustic turn-taking quality.

## Audio and lifecycle

Input, output and backend activity remain independent. Waveforms and the shared optional startup protection use browser media levels, not transcript arrivals, backend completion or append acknowledgments. The shared guard keeps original microphone capture running and can mute cloned outgoing tracks during an iOS opening; protection ends two seconds after first observed output activity, with a ten-second no-output escape. Studio no longer enables that opening mute: its outgoing tracks become available after the readiness acknowledgment and stay available during the greeting. The shared implementation and the independent FlowPath app remain unchanged. Microphone initialization and acoustic echo cancellation still belong to the browser; physical mobile echo and interruption remain separate acceptance checks.

Output quiet uses a 1.2-second observation window. This is a UI heuristic, not proof a sentence finished or that a user heard it. FlowPath uses it to advance its per-card briefing; long within-sentence pauses may need real-device tuning. Studio does not put generated assistant transcripts into cross-mode history as fully heard answers. User caption grouping is revisable; the backend keeps original fragments during the active session.

End requests `session.close`, keeps the sideband receiver alive, and awaits `session.closed` before releasing resources. A bounded timeout retains the latest duration as unconfirmed and invokes the hangup fallback. A successful HTTP hangup is not proof of final usage. Session duration snapshots are cumulative, never summed; backend token usage is separate. Existing app session-duration limits remain: Studio 120 seconds; FlowPath 600 seconds locally or 270 seconds on its hosted transport. These app limits do not create different voice quality tiers.

Both apps also use the shared inactivity policy. A session stays open while visitor input, assistant playback or backend work is active; after the configured quiet period the browser and server close the Live session. Studio publishers choose 30 seconds, one minute, two minutes or Never, with one minute as the default. The server remains authoritative so a backgrounded tab cannot leave a silent session charging. Tapping the waveform after an inactivity close starts a new session with the current bounded context.

## Studio pause and restart follow-up (September 13)

Two deterministic regressions reproduced old work surviving a quiet period: a new delegation ID could repeat a completed or failed request after 45 seconds without fresh speech, and repeated quiet audio/context reports could postpone the inactivity deadline. These are reproduced failure paths, not a recording-based diagnosis of the user's live session.

- `lib/visitor-realtime-control.ts` consumes the transcript versions belonging to completed and failed requests as well as cancelled requests. Overlapping trailing captions belong to the same request. A late delegation or acknowledgement alone cannot repeat that work or reserve another backend turn; fresh substantive speech still can. Rejected stale delegations emit bounded diagnostic metadata, without replaying results, showing Thinking, or resetting inactivity.
- Server audio reports only update the idle timer when input/output activity changes. `lib/use-visitor-session.ts` starts its idle timer once at readiness and changes backend activity only on transitions. Repeated owner acknowledgements, rendering and idle events do not restart its quiet deadline. Actual audio/backend work still keeps the session open under the existing publisher-selected timeout and hard session limit.
- `lib/visitor-realtime-session.ts` starts the voice model with empty message input rather than replaying old questions as input. The resumed controller supplies bounded earlier dialogue through reference-only thinking messages and explicitly waits for fresh speech; the backend retains the full bounded history separately from `latestRequest`. Restarting keeps the actual current view. It does not clear cards, automatically replay an answer, reissue a task, or add a paid retry. An explicit new request drives subsequent actions through the same validated/acknowledged navigation path.

## Publisher defaults and compatibility

Before opening paid voice, `VisitorTasksProvider.settle()` prepares the current publication's task session. Legacy entity kinds, relationship kinds and money units are descriptive labels; `adaptV1Catalog` converts them to valid, distinct task identifiers without changing published record IDs or source data. Compatible existing IDs remain unchanged; fallback IDs are deterministic within an immutable snapshot and independent of record order. Whitespace, punctuation, Unicode and encoding collisions must not block this preflight.

Task initialization emits bounded browser diagnostics under `stage: context`, `operation: workspace`, with timing, status and HTTP classification. It logs no content or raw error bodies. A failed preflight reports the API's public error in the voice UI and stops before microphone/provider startup; retry remains an explicit visitor action. Regression coverage lives in `tests/visitor-hierarchy.test.ts` and the legacy startup case in `tests/browser/visitor-realtime.spec.ts`.

The 2026-09-13 fix passed `npm run check` (422 server tests, 21 rendering tests, package consumer and build) and two isolated browser regressions for startup and shared chat/voice task state. The local GoSite task initialization endpoint changed from a schema error to a successful session. Audio/provider calls in browser tests were mocked; no paid voice session was started for this verification.

Every new Studio publisher defaults to voice using GPT-Live. Both legacy saved Standard and Premium values resolve to GPT-Live-1; their obsolete quality picker has been removed. Publisher tone, content, greeting and voice/chat choices remain configurable. The legacy recorded-turn provider returns 410 and asks callers to reconnect using the continuous session endpoint. The offline publisher preview remains deterministic and does not call a provider.

Studio's **End voice after inactivity** setting defaults to one minute and is persisted with the published visitor configuration. Existing saved settings without the field resolve to that default when read. `Never` is available for publishers who want the existing hard session cap to remain the only automatic boundary.

Studio's daily voice allowance now bounds session starts/openings and delegated backend tasks, not individual sentences spoken by the continuous frontend. Independent hard session limits bound voice duration, including small talk and silence. Live duration and backend token observations are operational measurements; they are not Stripe charges or reconciled monetary balances. The synthetic billing ledger and Stripe test controls remain separate and do not authorize live AI calls.
