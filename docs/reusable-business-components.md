Build the useful interactions once: browse, filter, sort, inspect, compare, select quantities, and calculate an estimate. Ingestion maps each publisher's approved information into shared contracts. Chat and voice invoke validated operations; browsing keeps its manual controls, while estimate edits use voice/chat only at the user's request. A model does not write a new menu, cart, calculator, or React implementation for each business. The runtime owns layout and Motion. Publisher-specific labels and fields supply meaning without requiring a separate restaurant, salon, or shop application.

## Cheapest practical incremental path

1. **Make imported data fit the existing primitives reliably.** Separate narrative pages from offerings; preserve units such as slice, whole item, session, hour, person or package; keep variant identity and unknown/conflicting prices explicit. Map reviewed photos to canonical records. Surface incomplete extraction and source conflicts before Apply. Use deterministic extraction where the source is explicit and model interpretation for meaning; evaluate stronger reasoning on failed semantic cases within a separately authorized budget rather than regenerating interfaces.
2. **Accept one browse → refine → compare → estimate chain across unrelated publishers.** The shared estimate component now shows published variants, quantities, line totals, subtotal, qualifications and tax status with existing Motion. Verify voice/chat quantity edits and display on desktop/mobile; estimate mutation buttons are intentionally absent. The broader imported price/description mapping remains a separate quality task: avoid repeating full source prose as a price while preserving actual conditions.
3. **Verify the implemented basket through task changes.** Exact record/field references supply every price; `set` replaces lines, `upsert` sets absolute quantities, `remove` deletes exact variants, and `clear` empties the basket. Reads and edits revalue published data. Confirm stale-revision rejection, historical presentation, Home/reopen and publication isolation in live acceptance. This remains a planning estimate until a real merchant adapter supplies a quote.
4. **Validate scoped tax reasoning before broadening it.** The implemented capability reuses retained evidence for matching lines after quantity edits, while new variants without classifications remain incomplete. A changed locality, fulfillment mode, date, classification or exemption needs an applicability review, often through recall rather than a fresh search. Tax evidence validation does not prove that the interpreted classification is correct. General fee/discount estimation is still outside this implementation.
5. **Add real integrations separately, one reusable adapter at a time.** An authenticated publisher may enable a supported inventory, quoting, scheduling or checkout adapter for that tenant. Prepare → review → explicit confirm → receipt/reconcile must remain distinct. Do not fork the platform for each subdomain or derive executable authority from a PDF. Synthetic fixtures remain the default development environment.

Expected cost advantage: arithmetic itself needs no model call; one language interpretation can choose existing capabilities, while cached published indexes and applicable retained research avoid redundant retrieval. Estimate edits still pass through the voice/chat path. Expected UX advantage: those channels share the same validated mutation and readable estimate, and visible values can be independently checked. These are architectural expectations, not measured savings or conversion results. Measure actual latency, paid calls, failure rate and user completion during bounded QA.

## Tax and estimate contract requirements

The current software contract is implemented; it is not a statement of any jurisdiction's current tax rules or a substitute for an authoritative tax adapter.

- An estimate carries its revision, publication, as-of date, line-level record/price-field references, quantities, units, currency, source qualifications and rounding method. The host calculates prices and line taxes using integer minor units with half-up rounding per line. No discounts, fees, conversions or unlisted adjustments are inferred.
- Tax input declares jurisdiction, transaction location, fulfillment, applicability notes and each line's classification/taxability. Research returns bounded `evidenceExcerpts`; researched mode selects `{resultId, excerptId}`, and the host resolves the exact retained cited span. The exact-quote input remains supported for retained rules. Both paths require a matching public citation, declared jurisdiction and supported taxable percentage. Every comma/parenthesis/slash-separated jurisdiction component must appear as whole phrases in one accepted excerpt; the host does not infer aliases or applicability. Retrieval age must be at most 24 hours and not future-dated; the basket date must be current. Result expiry also respects the visitor session and UTC day. These are provenance/freshness checks, not semantic proof of classification, effective law or exemptions.
- A visitor-supplied hypothetical rate may support a clearly labeled hypothetical calculation; it must not become a verified business rule. Researched evidence and publisher facts retain distinct authority even when the conversation is seamless.
- Quantity edits revalidate the retained tax input against matching record/field lines without a new search. A new unclassified line yields an incomplete result with null overall tax/total; unavailable retained evidence leaves tax uncalculated. Clearing the basket clears retained tax assumptions. Results retain sources, dates, notes and a hash binding the exact basket/publication/date.
- Back/Forward restores the previous presentation and assumptions; the current basket remains current and stale controls cannot overwrite it. A real adapter's quote would still need its own ID, expiry, terms, currency and confirmation boundary.

[Record context projection](../lib/visitor-task-record-context.ts) keeps query semantics, field meaning, exact collection scopes and confirmed IDs/order. Optional layout hints, prose and duplicate data can be omitted with explicit retrieval instructions; an identical ordered card-reference list can point to the unchanged confirmed directory. If a large basket needs further reduction, its exact revision, currency and ordered record/field/quantity references remain; `estimate.read` supplies omitted monetary and tax details before an answer. Repeated evidence-handle session/publication/generation values can share an exact `evidenceScope`; handle identity, authority, expiry and dependencies remain intact. When retained research exists, the bridge reserves at least 512 bytes before compaction and preserves the small relevant recall directory, including its ID, date, query and historical authority. Larger findings remain retrievable; an empty envelope is not added without findings. The 48,000-byte instruction ceiling is unchanged. ## Cross-domain quality gates

| Fixture | Required chain and edge cases |
| --- | --- |
| Food/menu | Show all offerings → vegetarian/other explicitly published category → price per requested size → compare → quantity subtotal. Keep slice versus whole-item prices distinct; unknown allergens are not safety assurances; photos remain correctly associated or honestly unlabeled. |
| Salon/services | Filter services by published duration and price → compare two services → estimate multiple services. Distinguish “from” prices, staff-dependent options and consultation-required prices. No inferred appointment availability or identical tax treatment. |
| Classes | Filter by subject, date or location → compare sessions/packages → estimate attendees. Preserve per-person versus per-session basis, age/prerequisite conditions, time zones, dates, and unknown capacity. |
| Products | Filter variants → compare compatible dimensions → adjust quantities → estimate. Preserve SKU/variant, currency, units and shipping/tax uncertainty. No inferred stock or checkout authority. |

For each fixture, verify browsing controls and mocked chat/voice routing, including voice/chat-only estimate edits; then run explicitly budgeted live chat and recorded speech acceptance. Check desktop/mobile layout, reduced motion, keyboard/focus, no-photo and long-name states, empty results, conflicts, source replacement/removal, publication revision changes, task cancellation, and Back/Forward/Home. An acknowledged display must match what is actually visible. A menu with 100 records and long descriptions must stay within context bounds using explicit omission plus retrieval, not lose the query or throw after rendering.

## Publication, privacy and implementation boundary

Original uploads, source anchors, corrections and unapplied proposals remain private. Only the current authorized publication feeds visitor records/media. Keep review → Apply to draft → Publish separate, preserve other sites, and require a new reviewed mapping when source changes invalidate a price or image association. Session selections/estimates belong to that visitor and publication, not a cross-tenant global memory.

Models may propose typed operations and select registered views; the host validates references, performs arithmetic, enforces bounds and executes enabled capabilities. This implementation adds no generated JavaScript, arbitrary formula evaluation, real financial transaction, infrastructure change or new dependency. The independent website remains usable while the assistant surface is closed or unavailable.
